## 1. 공통 개발 규칙 ⚠️ 전 배치 필수

### 1.1 "없다"고 결론내기 전에 전 파일을 확인할 것
루트 `CLAUDE.md` 원문:

> 검색이 안 되거나 작업이 막힐 때 **일부만 보고 단정하지 말 것**. 반드시 **전 파일**을 확인한 뒤 결론낸다.
> - **규칙**: 프론트는 파일이 여러 개다 → `public/static/*.jsx` **전부**(app·landing·counseling·counseling_admin) 훑고 결론낼 것. 백엔드도 라우트가 여러 곳일 수 있다.

이 지시서의 라인 번호는 **2026-09-19 시점 기준**이다. 파일이 바뀌었으면 라인 번호를 믿지 말고 **문자열로 다시 찾아라.**

### 1.2 기존 동작 무영향을 검증하며 진행할 것
루트 `CLAUDE.md` 원문:

> 새 기능을 넣을 때 **기존 동작이 깨지지 않음을 검증**하면서 간다(끝나고 몰아서 말고).
> 추가형으로 설계(기존 흐름 분기 최소·기존 컬럼/응답 유지), 기존 경로를 실제로 한 번 태워 보고, 데이터는 NULL 허용으로 기존 행 무영향.

**이 지시서의 수정은 대부분 보안·버그 수정이다. 응답 스키마를 바꾸는 수정은 프론트 호출부를 반드시 함께 확인해라.**

### 1.3 프론트는 빌드·200으로 런타임 에러를 못 잡는다
렌더 검증 필수(루트 `CLAUDE.md` `feedback_frontend_render_smoke`). `.jsx` 를 고쳤으면 실제 화면을 한 번 띄워봐야 한다.

### 1.4 복제 결함은 형제 서비스를 함께 고칠 것
트윈·파생 구조라 결함도 복제돼 있다. 각 이슈의 **"형제 서비스" 항목**을 반드시 확인해라.

| 결함 | 복제된 곳 |
|---|---|
| 리더보드 이메일 노출 | 마음게임 ↔ CTS 게임 |
| weekly-report IDOR | 마음게임 ↔ CTS 게임 |
| 번아웃 metadata 키 불일치 | 마음게임 ↔ CTS 게임 |
| `share/respond` 소유권 미검증 | 마음부부 ↔ 마음세대 |
| `external_orders`·`email_verified` DDL 누락 | 마음수달 ↔ 마음곁 |

### 1.5 ⛔ CTS는 유지보수 모드
루트 `CLAUDE.md` 원문:

> ⚠️ **CTS는 유지보수 모드 — 에러·버그 수정만, 신규 기능 금지**(사용자 확정 2026-07-18).

**이 지시서의 CTS 항목은 전부 보안·버그 수정이므로 허용 범위다.** 단 "겸사겸사" 기능 개선을 얹지 마라. 지시된 것만 고친다.

### 1.6 CTS는 서브모듈 — 커밋 순서
`cts-maum-main/` 은 별도 레포(`lightoflife-cts`)의 서브모듈이다.
```
cts-maum-main 내부 커밋 → push → 부모 레포에서 포인터 커밋 → push
```
`cts-game-main/` 은 **부모 레포 안에 있다**(서브모듈 아님). 헷갈리지 말 것.

### 1.7 서비스별 커밋 분리
서비스 간 변경을 하나의 커밋에 절대 섞지 않는다(선택적 revert를 위해).
```
[maumful] …   [cts] …   [maumgame] …   [maumcouple] …
[maumbubu] …  [maumsedae] …  [maumotter] … [maumgyeot] …  [공통] …
```

### 1.8 GitHub 계정 2개 — push 실패 시 가장 먼저 확인
```bash
gh auth status
gh auth switch --user youngjun1603   # 활성이 shine184280-hue 면 private 레포 push가 404
gh auth setup-git
```

### 1.9 배포
워커 배포(`wrangler deploy`)는 반드시 **포그라운드**. 배포 전 TypeScript 에러 확인.
마음수달·마음곁은 GitHub 웹UI → Cloudflare 자동배포(각 폴더 `CLAUDE.md`).

### 1.10 설계서도 함께 갱신
코드를 고쳤으면 해당 서비스 `docs/DESIGN.md` 의 관련 섹션과 §15 리스크 항목을 갱신하고, 문서 맨 아래 개정 이력에 한 줄 추가해라. **설계서를 낡게 두면 이 작업 전체가 무의미해진다.**

## 2. 이슈 항목 읽는 법

각 배치의 이슈는 아래 형식으로 되어 있다.

```
### [R-00] 제목
| 항목 | 내용 |
|---|---|
| 심각도 | S1 / S2 / S3 |
| 대상 | 서비스 · 파일 · 라인 |
| 형제 서비스 | 함께 고쳐야 하는 곳 (없으면 —) |
| 근거 | 설계서 §번호 |

**무엇이 문제인가** — 현상과 왜 위험한지
**확인 방법** — 실행 가능한 명령. 고치기 전에 재현부터 할 것
**구현 방법** — 무엇을 어떻게 바꿀지
**검증 방법** — 고친 뒤 무엇을 확인해야 끝난 것인지
**주의** — 함정, 건드리면 안 되는 것
```

### 2.1 ⚠️ "구현 방법"은 지시이지 정답이 아니다
이 지시서는 **2026-09-19 시점의 코드를 읽고 쓴 것**이다. 실제 코드를 열었을 때 전제가 다르면:
- 지시대로 밀어붙이지 마라
- 결과 보고서의 **"전제 불일치"** 항목에 무엇이 달랐는지 쓰고
- 더 나은 방법이 있으면 그걸 택하되 **왜 그랬는지 반드시 남겨라**

### 2.2 판단이 필요하면 멈출 것
다음은 임의로 결정하지 말고 사용자에게 물어라.
- 가격·상품 구성 변경
- 사용자에게 보이는 문구·안내 변경
- 데이터 삭제를 수반하는 마이그레이션
- 기존 사용자의 권한·이용권에 영향이 가는 변경
- 이 지시서에 없는 결함을 발견했는데 수정 범위가 큰 경우

### 3.2 보고서 작성 원칙
1. **못 한 것을 숨기지 마라.** 부분 완료·미착수가 있는 보고서가 전부 ✅인 보고서보다 신뢰할 수 있다.
2. **검증 항목은 실제로 실행한 것만 체크해라.** "될 것이다"는 검증이 아니다.
3. **전제 불일치와 새 발견은 이 작업의 가장 큰 산출물이다.** 코드를 직접 연 사람만 알 수 있는 것이다.
4. 원격 DB 확인이 필요한 항목(`partner_commissions` 실재 여부 등)은 **확인했으면 결과를, 못 했으면 못 했다고** 써라.

## 4. 배치 완료 기준

배치 하나가 끝났다고 하려면 아래가 전부 충족돼야 한다.

- [ ] 지시된 이슈를 전부 처리했거나, 못 한 것의 사유가 보고서에 있다
- [ ] 형제 서비스 복제 결함을 함께 고쳤거나, 안 한 사유가 있다
- [ ] 각 수정에 대해 기존 동작 무영향을 **실제로 태워 보고** 확인했다
- [ ] 프론트를 고쳤으면 렌더 검증을 했다
- [ ] 서비스별로 커밋이 분리돼 있다
- [ ] 해당 서비스 `docs/DESIGN.md` 와 `_docs/RISKS.md` 를 갱신했다
- [ ] 결과 보고서를 작성했다
- [ ] 배포했거나, 배포하지 않은 사유가 보고서에 있다
